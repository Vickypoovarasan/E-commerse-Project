Authentication, OTP, CSRF, Token Lifecycle, and Client Flows
Token lifecycle and storage policy

Access token: TTL = 15 minutes; stored only in volatile JS memory or sessionStorage under strict CSP; passed in Authorization: Bearer <token> header. Do not store long‑lived tokens in localStorage in production.

Refresh token: stored in HttpOnly, Secure, SameSite=Strict cookie (use SameSite=Lax only for documented payment redirect callbacks). Refresh tokens are rotated on each refresh; old refresh tokens invalidated.

Refresh endpoint: POST /api/auth/refresh — refresh cookie sent automatically; response JSON { "accessToken":"...", "expiresIn":900 }.

Registration and secure OTP flow

Registration fields: username, email, password, phone_number, address (street, city, state, country), date_of_birth.

Passwords hashed with BCrypt. is_verified = false until OTP verified.

OTP generation: 6‑digit numeric code; store only a cryptographic hash (HMAC‑SHA256 with server pepper) in users.otp_code_hash; set otp_expiry = now + 5 minutes. Use constant‑time comparison for verification.

Rate limits: max 3 OTP generation requests per hour per user/IP; 60s resend cooldown; max 5 verification attempts per OTP — exceeding invalidates OTP and requires new request.

debug_otp: returned only in development profile (spring.profiles.active=dev or app.security.debug-otp-enabled=true). Add CI build test to fail production builds if debug OTP is enabled.

Password reset

Use cryptographically random UUID token stored hashed (SHA‑256) with 1‑hour TTL and single‑use semantics.

CSRF double‑submit cookie

Backend issues cookie XSRF-TOKEN (Secure; SameSite=Strict). Client reads cookie and attaches header X-XSRF-TOKEN for all state‑changing requests (POST/PUT/DELETE). Document exact client extraction method.

Global fetch wrapper and silent refresh sequence (client)

Global wrapper attaches Authorization header and X-XSRF-TOKEN header for state changes.

On 401 Unauthorized indicating expired access token:

Push failed request into retryQueue.

If refreshing flag is false: set refreshing = true and POST /api/auth/refresh.

On refresh success: update volatile accessToken, set refreshing = false, retry queued requests with new header.

On refresh failure (401): clear queue and redirect to auth.html.

If refreshing flag is true: wait for completion then retry queued requests.

Implement transparent retry logic and queueing to avoid duplicate refresh calls.

Checkout, Inventory Concurrency, Payments, Idempotency, and Order Rules
Monetary rules

Sales tax = 12% applied to subtotal.

Shipping = $15.00 flat; free if subtotal > $150.00.

Use DECIMAL(10,2) for all monetary calculations and storage.

Checkout transactional contract

Endpoint: POST /api/orders/checkout. Require header Idempotency-Key (client generated).

Persist idempotency keys in idempotent_requests table: key_hash CHAR(64) (SHA‑256 hex), response_payload VARCHAR(10000), created_at TIMESTAMP. TTL: 24 hours. On duplicate key within TTL return cached payload with header Idempotency-Cache: hit.

Transactional behavior:

Use @Transactional(isolation = Isolation.REPEATABLE_READ).

Default optimistic locking on products via version column. On ObjectOptimisticLockingFailureException retry up to 3 times with exponential backoff 100ms → 200ms → 400ms. If still failing return HTTP 409 with code: "CONFLICT_STOCK".

For hotspots, use pessimistic write locks (SELECT ... FOR UPDATE).

Re‑verify stock inside transaction before commit; throw InsufficientStockException if any item would go negative.

Deduct stock, create orders and order_items, compute expected_delivery_date = order_date + 4 days, persist idempotency response, commit.

Payment simulation and refunds

POST /api/payments/create-payment-intent requires Idempotency-Key. Simulate Razorpay order_id and return payment_id.

Refunds must be idempotent: store refund_id and check before issuing a refund. Wrap refund and DB updates in a single transaction.

Order lifecycle rules

cancelOrder allowed if now - order_date <= 3 days. On cancel: set status = CANCELLED, restore stock transactionally. If payment_method = RAZORPAY and payment_status = PAID, create refund, set payment_status = REFUNDED, store refund_id. If payment_method = COD, set payment_status = CANCELLED.

requestReturn allowed if status = DELIVERED and now - actual_delivery_date <= 1 day. Set status = RETURN_REQUESTED.

Admin approve-return sets status = RETURNED, restocks items, and refunds if paid online.
